# 工具调用可靠性改进清单

目标：用户明确要求记录、修改或查询时，系统能选对操作、真实执行、核验结果，并如实反馈。按顺序逐项完成；每项验收通过后再开始下一项。

## 2026-10-13 实施进度

本轮已落地本地代码和自动化回归：自报耗时/新待办使用专用结构化规划，其他明确写入使用通用逐项规划；执行前校验参数、去重同轮重复项，按每项结果组织最终回复。计时生命周期保留专用路径，今日重点设置需确认，导出不会误入写入规划。操作账本能计算执行、确认、失败、去重和核验失败指标；回合事件保留原话、最终回复和操作状态供本地人工复核，并提供明确触发的匿名化诊断导出，不含文本、参数值或 ID。DOM 回归 323 项通过，仍不代表真实模型选工具准确率已达标。

- 阶段 0：已有脱敏真实漏记案例及正例、近似负例、多项请求、疑问句和信息不足样本；仍缺多种真实失败类型，不能计算可信的历史基线。
- 阶段 1：专用和通用规划都逐项拆分操作、记录状态和缺失字段；操作账本保存原话、参数来源、目标、确认要求及执行回执。模型规划仍可能漏识别原话中的子项，需真实模型评测发现。
- 阶段 2：所有明确写入都进入受限的结构化规划或专用计时路径，执行前校验工具名和参数；查询、导航和导出留在普通工具路径。通用写入规划器已清理 6 个残留但未实现的旧工具名；真正的职责合并仍未做。
- 阶段 3：稳定实体、关键 meta 和 localStorage 写入均按引用读回核验，删除操作核验读回为空；同轮重复写入通过幂等键合并，确认草稿与正式写入分开。错误已区分参数、业务、网络和持久化类别；同一幂等键只允许可重试错误再尝试一次，其他错误不会自动重试。
- 阶段 4：明确写入不先流式展示模型完成态；最终答复依据账本逐项报告待确认、缺信息、失败、合并或成功/核验状态。仍无法独立证明模型规划阶段没有漏列用户子项。
- 阶段 5：确定性路由样例评测和 323 项端到端 mock 回归纳入 `verify:all`。评测不调用真实模型，尚未记录真实模型工具选择、参数与最终反馈指标。
- 阶段 6：未启用影子运行或分阶段上线观察。本项目是浏览器本地应用，真实运行观察需要在用户自己的模型配置和数据上完成；当前环境没有可信的线上样本和测量结果。

## 推进规则

- 一次只实施一个未完成项，完成后跑该项的验收和项目相关检查。
- 先记录基线和复现用例，再改执行逻辑，避免只靠提示词感觉变好。
- 保留真实工具轨迹；每项操作都区分“未调用、待确认、执行失败、执行成功、已核验”。
- 涉及用户确认的写入，在确认前不得落库，也不得反馈为已完成。
- 不以增加提示词长度作为唯一修复。优先用确定性代码约束和可验证状态。

## 清单

### 0. 建立问题样本和基线

- [ ] 收集并人工标注真实漏调、错调、错参数、重复调用和假成功案例；本地已有回合事件与匿名化诊断导出入口，仍需用户在真实运行中抽查并补充样本。
- [x] 为每个案例标注用户意图、预期操作、必要字段、是否需要确认、正确的最终反馈。
- [x] 建立正例、近似负例、多意图和信息不足四类样本；覆盖自然表达和省略表达。
- [ ] 统计真实模型工具选择正确率、漏调率、误调率、参数正确率和反馈准确率；当前账本可给执行/核验指标，真实意图标签需人工评审。

验收：样本能稳定复现已知问题；同一组样本可以重复跑并得到可比较的指标。

### 1. 定义统一的操作意图和状态

- [x] 为每个用户请求拆分一个或多个操作项，不把多个写入合并成一句“已处理”。
- [x] 统一操作状态：`requested`、`needs_info`、`awaiting_confirmation`、`executing`、`failed`、`succeeded`、`verified`。
- [x] 每项记录用户原话、规范化操作、目标对象、参数来源、待补字段、确认要求和结果。
- [x] 明确“用户要求登记”与“用户只是在讨论登记”的区别；信息不足时只追问缺失字段。
- [x] 支持一轮多项操作，并逐项保存状态，避免完成第一项后遗漏其余项目。

验收：给定多项请求时，系统能列出完整操作项；缺字段或需确认的项不会被误标为完成。

### 2. 让代码接管确定性路由和执行约束

- [x] 将高频、低歧义操作接入确定性路由或明确的界面快捷操作。
- [x] 意图由模型判断后，代码校验工具名、参数、目标对象和用户授权，再允许执行。
- [x] 对已明确路由的操作使用指定工具调用或直接调用领域函数，避免再次让模型从全部工具中自由选择。
- [ ] 合并职责重叠或容易混淆的工具；在保留必要区分时，让工具描述明确说明适用场景和相邻工具的区别。
- [x] 为参数定义 JSON Schema、必填字段、枚举范围和数值边界；执行层再次校验，不能只信模型输出。

验收：已确认的测试样本稳定映射到预期操作；未授权、越界或参数不完整的调用会被代码拒绝或转为追问。

### 3. 建立执行回执、持久化核验和幂等

- [x] 工具统一返回结构化结果：状态、操作 ID、记录 ID、简短说明、是否需要确认、错误码和可重试标记。
- [x] 写入成功后按记录 ID 读回数据，确认目标、时间、时长和内容与请求一致；稳定实体和关键 meta 状态已覆盖，删除操作核验读回为空。
- [x] 为一次用户请求及其各子操作分配稳定 ID；同轮重复操作不会重复创建记录或重复扣加数值。
- [x] 将参数错误、业务拒绝、网络错误和持久化失败映射为不同错误码；网络错误才标记为可重试，执行层不盲目自动重试。
- [x] 对“草稿已生成”和“正式写入成功”采用不同状态和不同用户文案。

验收：可通过测试注入失败、超时、重复提交和部分成功；结果状态正确，重复请求不产生重复记录。

### 4. 用操作状态约束最终回复

- [x] 最终回复逐项对应本轮操作清单，展示每项是已核验、待确认、缺信息还是失败。
- [x] 只有工具成功且读回核验通过，才允许使用“已登记/已保存/已完成”等完成态表述。
- [x] 若有操作漏调，系统必须继续执行、明确询问缺失信息，或说明尚未完成；不能静默跳过。
- [x] 避免工具尚未返回时先流式输出完成态结论；必要时暂存结论，待执行结果到达后再发送。
- [x] 多项操作部分成功时，逐项报告，不把整体说成全完成或全失败。

验收：注入“工具未调用、失败、待确认、部分成功、核验不一致”结果时，回复与实际状态逐项一致。

### 5. 建立工具选择评测和回归门槛

- [x] 将第 0 项的样本做成自动化评测，检查确定性路由、参数校验和确认要求。
- [x] 分别评测路由、执行结果、最终回复，不用“工具函数单测通过”替代端到端验证。
- [ ] 基于人工标注的真实模型回合事件记录漏调率、误调率、参数错误率和完成态误报率；重复写入率、执行失败率、核验失败率已有本地账本统计，尚无真实样本基线。
- [x] 每次改提示词、工具定义、模型、路由或执行循环后跑本地回归集。
- [ ] 对匿名化导出的真实失败案例补充回归样本；人工抽查模型评测无法可靠判断的复杂案例。

验收：已知失败样本持续通过；关键指标达到项目设定阈值后，才扩大自动执行范围。

### 6. 分阶段上线并观察

- [ ] 先以影子模式记录系统拟采取的操作，不实际写入，比较模型判断和人工预期。
- [ ] 通过基线后，先开放低风险、可撤销的记录操作；高影响操作保留确认。
- [ ] 观察漏调、误调、重复写入和假成功反馈；出现回归时能按操作 ID 定位并修复。
- [ ] 根据真实失败样本更新路由、Schema、工具描述和评测集，再逐步扩展操作范围。

验收：小范围运行达到第 5 项设定的指标；失败可以追踪、复现和回滚，再进入下一阶段。

## 当前已知起点

- 工具通过 function calling 暴露给模型；常规情况下由模型自行选择工具。回合级事件保存在本地，用户明确请求 `export_action_diagnostics` 时可导出匿名化结构数据；人工查看和补标签仍是外部步骤。
- 有工具描述审计和工具调用轨迹，但描述审计不等于模型选择评测。
- 有部分确定性命令路由、待确认草稿和承诺类操作确认机制。
- 提示词已有记录纪律，但仍需代码层面的执行状态和结果核验兜底。

下一步应先持续收集脱敏真实漏调/错调样本，再扩展确定性执行范围；在真实模型评测和本地运行观察前，不应把通用工具调用描述为已达标。
