# My Study Agent 技术学习笔记

## 1. 这份文档的用途

这不是产品需求，也不是实现清单。它记录本项目在设计过程中提炼出的工程方法，解释每项方法解决什么问题、应如何落地，以及不适用时应如何收敛。

核心结论是：不要寻找“一个数据库解决所有问题”。应根据数据是否需要长期保留、访问延迟、查询方式和恢复成本，选择合适的存储与运行组件。

## 2. 按数据生命周期分层

### 方法

把数据分成三类：

| 数据类型 | 典型内容 | 合适组件 | 关键要求 |
|---|---|---|---|
| 业务事实 | 学习目标、任务、资料元数据、答题记录、复习日期 | MySQL | 可事务写入、可导出、可删除、可恢复 |
| 活跃状态 | 最近聊天窗口、当前答题草稿、短时互斥锁 | Redis | 低延迟、有 TTL、允许丢失后重建 |
| 检索投影 | 资料 chunk、关键词索引、向量 | Elasticsearch | 面向全文/语义检索、可全量重建 |

### 为什么

学习记录会影响后续计划和复习，不能因为缓存过期而丢失；聊天上下文每次都查询关系库会慢，但丢失后可重建；资料问答需要关键词和语义相似度检索，不适合用普通关系查询完成。

### 落地规则

- MySQL 是业务事实来源。任何已确认的答题、计划完成状态和复习安排，必须先写入 MySQL。
- Redis 只能缓存可重建的数据。缓存失效不应导致已提交答案或完整会话历史消失。
- Elasticsearch 只保存搜索副本。索引损坏时必须能从资料主记录和原文件重新构建。

## 3. 缓存不是主库：先持久化，再缓存

### 方法

对会改变学习状态的操作采用以下顺序：

```text
校验请求 -> MySQL 事务提交 -> 更新/删除 Redis 缓存 -> 异步更新检索索引或派生任务
```

### 为什么

如果先写缓存、后写数据库，数据库失败时用户可能已经看到“已提交”的状态，但实际学习记录已经丢失。反过来，缓存更新失败最多造成下一次请求回源查询，事实数据仍然存在。

### 例子：提交练习答案

1. 校验该题属于当前用户，答案格式正确。
2. 在一个事务中写入 `practice_attempts`，更新知识点掌握度，并更新或创建 `review_schedules`。
3. 提交事务后，使当天计划缓存失效。
4. 如果需要生成讲解或统计，投递异步任务。

### 幂等性

网络重试会导致同一提交到达多次。客户端为每次提交生成 `request_id`，服务端在 MySQL 中对 `(user_id, request_id)` 建唯一约束，重复请求直接返回第一次的结果。不能只依赖 Redis 锁实现幂等，因为锁会过期或缓存可能不可用。

## 4. Redis 的正确使用方式

### 4.1 对话窗口与 TTL

对话上下文应限制最近消息数和总 token，而不是无限累积。建议起点：最多 20 条原始消息，TTL 为 1 小时，正常访问时滑动续期。

超过窗口的早期消息保留在 MySQL；用于 Agent 的上下文使用滚动摘要加最近消息组成。摘要必须标注来源会话版本，避免旧的异步摘要覆盖新的会话状态。

### 4.2 大 key 控制

一条 Redis key 过大时，序列化、网络传输和删除操作都会变慢。缓存消息窗口可按固定条数分片，例如每 10 条消息一个 chunk；使用一个 metadata key 记录分片数和版本。不要把完整资料全文、所有聊天记录或长期学习档案放入一个 Redis key。

### 4.3 锁的边界

Redis 锁只用于降低并发冲突，例如避免同一会话的两次消息同时更新窗口。锁必须有短 TTL，并且业务正确性仍由 MySQL 事务、唯一约束或乐观锁保证。

### 4.4 缓存失效后的行为

| 缓存内容 | 失效后的处理 |
|---|---|
| 最近对话窗口 | 从 MySQL 查询会话摘要和最近消息并重建 |
| 今日学习任务 | 直接查 MySQL，再按短 TTL 回填 |
| 当前练习草稿 | 提示草稿不可恢复；已提交答案仍从 MySQL 查询 |
| 分布式锁 | 允许重新竞争，依赖幂等约束防止重复写入 |

## 5. RAG 的正确边界

### 5.1 文档主数据与索引分离

原始资料、归属关系、解析状态、内容哈希和删除状态应保存在 MySQL 与文件存储中。Elasticsearch 仅保存按段落切分后的可搜索 chunk。这样能够做到：

- 更新资料时按 `content_hash` 判断是否需要重建索引。
- 资料删除时，删除主记录、原文件和关联 chunk。
- 检索索引发生映射冲突或数据损坏时，执行全量重建。

### 5.2 混合检索

两种检索互补：

| 通道 | 擅长内容 | 局限 |
|---|---|---|
| BM25 关键词检索 | 专有名词、公式名、精确术语 | 对同义改写不稳定 |
| 向量检索 | 语义相近的解释、自然语言提问 | 对精确字面匹配可能较弱 |

建议两路并行召回，再用 Reciprocal Rank Fusion（RRF）融合排序。RRF 只依赖各通道的名次，不要求不同通道的分数可比较：

```text
RRF(document) = sum(1 / (k + rank_i))
```

其中 `rank_i` 是文档在第 `i` 个通道的排名，常用 `k = 60`。向量服务或 embedding 调用失败时，可降级为 BM25 并明确记录降级事件；两路都失败时返回检索不可用，而不是编造引用。

### 5.3 chunk 切分与引用

- 优先按标题、段落和列表等语义边界切分，保留少量重叠。
- chunk 大小按模型 token 预算配置，不按固定字符数硬切。
- 每个 chunk 保存 `document_id`、`chunk_no` 和 `source_locator`。
- 回答中展示资料标题和来源定位；模型输出的结论必须能回溯到使用的 chunk。

### 5.4 权限过滤优先

无论是 BM25 还是向量检索，查询本身必须带上 `user_id` 和可访问 `subject_id` 过滤。不能先检索全部资料、再在应用层丢弃无权限结果，因为无权限文本已经可能影响排序、日志或模型上下文。

## 6. 关系数据模型的设计原则

### 6.1 区分事件、状态与派生结论

| 类型 | 例子 | 存储方式 |
|---|---|---|
| 不可变事件 | 一次答题、一次消息、一次任务完成 | 追加记录，如 `practice_attempts`、`conversation_messages` |
| 当前状态 | 目标是否完成、某题下次复习日 | 可更新记录，如 `learning_goals`、`review_schedules` |
| 派生结论 | 掌握度、学习偏好、会话摘要 | 可重算或带版本更新的记录 |

这能避免一个字段既要记录历史又要表示当前状态。例如，题目是否答对应该在每次作答中保存，而不是只覆盖 `practice_items` 上的一个布尔值。

### 6.2 长期记忆应可解释、可管理

长期记忆只记录跨会话有帮助的信息，例如解释偏好、稳定薄弱点或已确认的学习目标。每条记忆都应有来源、置信度、状态与删除能力。

模型可以产生候选记忆，但不能直接视为事实。激活前应经过规则验证或用户确认；被删除或标记为失效的记忆不能再次加入上下文。

### 6.3 乐观锁与版本

多个请求可能同时更新学习偏好、会话摘要或掌握度。为可合并的状态表保留 `version` 字段：更新条件使用 `WHERE id = ? AND version = ?`，成功后递增版本；冲突时重新读取、合并并重试。对答题记录这类追加事件，优先使用唯一键和事务而非覆盖更新。

## 7. 间隔复习应先可解释，再追求复杂算法

复习系统要将“答案结果”转化为“下一次学习动作”。第一版可采用固定且可解释的间隔：

| 结果 | 下一次间隔 | 处理 |
|---|---:|---|
| 首次答对 | 1 天 | 建立复习节奏 |
| 连续答对 | 3、7、14、30 天递增 | 增加间隔 |
| 答错 | 1 天 | 创建错题复习任务并提供讲解 |
| 无法判定 | 不自动更新 | 请求学习者确认或重新作答 |

将算法封装在 `ReviewScheduler`。它的输入是既有排期与本次结果，输出是新间隔、到期时间和状态。这样未来替换为 SM-2 或 FSRS 时，只替换调度策略，不更改历史答题表和 API 契约。

## 8. Agent 通过受限工具改变状态

模型适合判断意图、组织讲解和提出建议，不适合直接执行数据库修改。将 Agent 的写操作限制为明确的工具：

- `search_study_materials(subject_id, query)`
- `create_learning_task(subject_id, type, title, instruction)`
- `create_practice_item(subject_id, knowledge_item_id, question)`
- `submit_practice_attempt(item_id, answer, request_id)`
- `propose_learning_memory(content, source_session_id)`

每个工具在服务端执行身份校验、输入校验、事务处理和审计。模型生成的工具参数不可信，尤其是资料 ID、用户归属、日期和删除动作必须在工具层二次校验。

## 9. 异步任务、Outbox 与可重试性

不应把文档解析、向量生成、全文重建、会话摘要和候选记忆提取放在 HTTP 请求主链路中。主事务中写入事实数据和一条 outbox 事件；后台 worker 读取事件并执行工作。

```text
MySQL 事务：保存资料记录 + 保存 outbox 事件
  -> worker：解析资料、生成 chunk、写 ES
  -> 成功：记录处理版本和完成时间
  -> 失败：增加重试次数；超过阈值标记失败并提示用户重试
```

事件必须有稳定 ID 和去重键。worker 至少一次投递是常态，因此索引与摘要更新必须具备幂等性：相同资料版本重复处理不应产生重复 chunk；旧版本任务不得覆盖新版本的解析/摘要结果。

## 10. 可观测性只记录运行事实，不记录学习正文

### 指标

记录请求量、请求延迟、模型调用耗时和失败率、检索耗时、索引任务积压、Redis/MySQL/ES 错误数。指标标签只使用低基数维度，例如路由、操作类型、状态码和模型名。

### Trace

一次请求创建一个根 span；上下文读取、资料检索、模型调用、判题和数据库写入创建子 span。使用脱敏的请求 ID 关联日志和 Trace。

### 隐私边界

禁止写入指标、日志或 span 属性的数据包括：对话正文、资料正文、学习者答案、访问令牌、数据库密码及完整用户标识。对排障有价值的是操作类型、耗时、错误码和数据量级，不是原始学习内容。

## 11. 渐进式交付与验证

组件复杂度应跟随真实需求增长：

1. 先实现 MySQL 学习主数据和 Redis 会话缓存，验证学习记录不丢失。
2. 资料量与问答需求增长后加入 Elasticsearch 混合检索，验证引用可追溯、索引可重建。
3. 加入复习调度和后台任务，验证重复消息/重复任务不会造成重复状态。
4. 服务稳定后接入指标、Trace 和看板，验证无敏感内容泄漏。

每一步至少覆盖一个故障演练：清空 Redis、重试同一提交、删除检索索引、重复执行 outbox 事件、模拟 embedding 失败。通过这些演练确认系统具备预期的降级与恢复能力。

## 12. 开发前检查清单

- 这条数据是否是业务事实？是则写 MySQL，而不是只写 Redis/ES。
- 这条缓存失效后，是否能从事实数据恢复？不能则不应放 Redis。
- 这条索引是否能从资料和数据库重新生成？不能则补足主数据来源。
- 这项模型操作是否会改变学习状态？会则必须经过受限工具、校验和事务。
- 这项后台任务重复执行是否安全？不安全则设计去重键和版本控制。
- 这个指标或日志字段是否包含学习正文或个人数据？包含则删除、脱敏或改为聚合值。
